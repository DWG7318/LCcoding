# Migration from 2.0.0 to 2.1.0

## Mainline continuity

The LCCoding mainline, four phases, two Owner Acceptance boundaries, centralized security closure, and protected Delivery remain unchanged.

## Existing engineering mode

For an existing engineering project:

1. Run Project Initialization in EXISTING mode.
2. Preserve repository identity, Git history, files, declared version, materials, and valid evidence.
3. Record current Git HEAD, version or `UNKNOWN`, runnable candidate, and prior project-state claim.
4. Mark inherited completion as `CLAIMED_UNATTESTED`.
5. Obtain Owner `CONTINUE`, `NARROW_REDIRECT`, `HOLD`, or `TERMINATE` before engineering.
6. Use runnable UI as the first Owner-visible cognition anchor, then trace Workflow, state, data, permissions, failures, recovery, and invisible evidence through existing maps.
7. Reuse valid evidence; keep unknowns explicit; route only real gaps into existing Feature Slices and Loop Runs.
8. Classify Project Health as `ATTESTED_COMPLETE`, `NEEDS_GAP_CLOSURE`, `PARTIAL`, `DIRECTION_CHANGED`, or `NOT_CONTINUING`.

Do not reset the project to `0.0.1`, rewrite history, treat UI as completion proof, or manufacture old LCCoding receipts retroactively.

## Proportional depth

Update Project Fingerprint to record product uncertainty, system coupling, real risk, irreversibility, and novelty. Template-default `UNKNOWN` is a valid unresolved record, but it requires assessment, rationale, and conservative deeper coverage before depth can be judged sufficient. Record the resulting depth rationale and any deeper analysis, material, or evidence coverage. Keep every mandatory mainline node and keep `recommended_loop` topology-only.

## Learning return

Leave Product learning blank unless it changes a future decision, constraint, check, template, or evidence-reuse rule. If consequential, update one existing canonical artifact. Do not create a learning phase, repository, directory, or mandatory document.
