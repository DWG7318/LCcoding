# LCCoding 2.7.0 Structure Consolidation Design

**Status:** Design direction approved; this written specification awaits independent Supervisor review and Owner review.

**Base:** LCCoding `2.6.0`, commit `3a39ab637e49f5456d4e3cd4d039800c2ce6eda2`.

**Provisional target:** LCCoding `2.7.0`.

**Document role:** non-normative design candidate. It authorizes no method, contract, template, validator, BI, installed-skill, release, or runtime change by itself. Only a later Owner-approved implementation may transfer these decisions into the normative LCCoding surfaces.

## 1. Decision summary

LCCoding 2.7.0 will keep the four-phase lifecycle and replace its duplicated documentation structure with one semantic authority and mechanically traceable projections.

The recommended architecture is:

```text
Owner authority
→ CONSTITUTION: immutable principles and Owner rights
→ SPEC: sole complete semantic authority, with stable clause IDs
→ contracts / schemas: machine-readable shapes and gates
→ templates: artifact instances constrained by contracts
→ SKILL / README / references: concise, source-linked projections
→ validators / tests: semantic and compatibility proof
→ BI: isolated read-only product implementation and projection compatibility
```

The lifecycle remains four phases. The semantic correction is:

```text
INITIAL
→ PRODUCT_FORMATION
  Calabash Draft
  → Product Simulation foundation
  → separately runnable Workflow / UI / Simulation
  → Mandatory Calabash Upgrade
  → Product Baseline
→ REAL_PRODUCT_INTEGRATION
  compatibility machine ID: ENGINEERING_RUNS
  Feature Slice
  → UI-locked real integration and end-to-end proof
  → required integration Run acceptance aggregate
→ DELIVERY_PREPARATION
  security closure
  → Post-Security Owner Acceptance
  → delivery decisions and package protection
```

SLK, CLK, GLK, and compatible registered execution methods remain a horizontal Run-execution axis available in every phase. They are not lifecycle nodes and do not advance a phase merely by completing a Run.

## 2. Goals

1. Make every normative claim have one authoritative definition.
2. Make every non-authoritative projection mechanically traceable to stable normative clauses or contracts.
3. Correct the Product Formation and Real Product Integration phase boundary without redesigning the mainline.
4. Give each recurring term one meaning and one preferred human name.
5. Separate Run-start input from Run-end Owner receipt.
6. Preserve cross-phase execution while limiting `ALL_REQUIRED_RUNS_ACCEPTED` to required Phase-3 integration work.
7. Consume Calabash 2.5.0 boundaries by reference rather than copying Calabash internals.
8. Keep UI, Workflow, Simulation, Product Baseline, and Primary product mainline semantics precise and non-duplicated.
9. Separate BI method boundary, product contract, implementation, compatibility, and release responsibilities.
10. Centralize shared Loop Control policy while retaining verified method-local controls until trustworthy bindings and runtime attestations exist.
11. Invalidate stale security closure and Post-Security Owner Acceptance when later work changes the covered product or security surface.
12. Reduce Owner and maintainer cognitive load without using deleted line count as a success metric.

## 3. Non-goals

- No new lifecycle phase, lifecycle axis, execution method, Agent, runtime, service, or status authority.
- No redesign of the four-phase mainline.
- No replacement of Calabash, SLK, CLK, GLK, or their internal methods.
- No migration away from the machine ID `ENGINEERING_RUNS` in 2.7.0.
- No new phase-gate ID or status field; the validated and accepted Product Baseline Handoff is the existing phase boundary evidence.
- No second project-status system; `status.json` remains authoritative.
- No BI rewrite, UI redesign, or dependency removal merely to make the repository look smaller.
- No deletion of required BI source, lockfiles, security checks, installer logic, or evidence contracts.
- No line-count quota, automatic bulk deletion, or formatting-only rewrite.
- No deployment of the global installed LCCoding skill during design or before the 2.7.0 merge and release are accepted.

## 4. Owner-locked decisions

The following are inputs to this design, not alternatives still awaiting selection:

1. The four phases remain.
2. Product Formation includes Calabash Draft, Product Simulation foundation, separately runnable Workflow/UI/Simulation, Mandatory Calabash Upgrade, and Product Baseline.
3. Real Product Integration begins with Feature Slice.
4. `ENGINEERING_RUNS` remains only as a compatibility machine ID; the English and Chinese human names are `REAL_PRODUCT_INTEGRATION` and `真实产品集成`.
5. Execution methods are cross-phase and never embedded as a mainline node.
6. Feature Slice inherits verified Workflow capability and may improve it only through governed impact analysis.
7. Real integration proves UI action → real API/MCP-backed Workflow → real state/data/side effect → visible UI result, with Product Simulation covering the same capability and failures.
8. A single semantic authority replaces repeated long-form definitions.
9. `RUN-HANDOFF.md` becomes Run-start input; `LOOP-OWNER-ACCEPTANCE.md` remains the end receipt.
10. Calabash is product definition/governance. Snake and Scorpion are cross-cutting definition dimensions, not Agents or layers.
11. UI lock is one-way Owner authority.
12. UI, Workflow, and Simulation are peer logical subtrees inside one total project repository; worktree is temporary construction isolation only.
13. Implemented Workflow exposes API and MCP for the same real capability. CORE/EXTRA is business necessity, not a technical layer.
14. One Owner-confirmed Primary product mainline determines proving priority without discharging other CORE obligations.
15. BI remains built-in, unified, installed once, and read-only.
16. `LCCODING_LOOP_CONTROL` is shared policy, not a fourth execution method and not a runtime.
17. Later product/security-surface changes invalidate affected security closure and Owner acceptance.
18. Historical design material remains history, not live normative authority.

### 5.4 Reference-graph weakness

`SPEC.md` currently contains no direct links to the topic references it is supposed to govern. The active references are mostly reachable only by filename knowledge. Conversely, README and SKILL sometimes restate rules instead of linking the authoritative clause.

The result is a document set, not an authority graph.

## 6. Considered structures

### Option A — surgical patch and prose pruning

Correct `phases.json`, edit the obvious phase paragraphs, trim README/SKILL, and leave the present document roles intact.

**Benefits:** smallest immediate diff; lowest migration cost.

**Costs:** duplication remains structural. The next semantic change again requires coordinated edits across five or more files. BI compatibility and historical authority remain unresolved.

**Decision:** not recommended. It treats symptoms while preserving the cause.

### Option B — single semantic core with layered projections

Make SPEC the sole complete semantic authority, give its claims stable clause IDs, narrow Constitution to constitutional law, and turn README/SKILL/references into source-linked projections. Keep contracts/templates machine-oriented and isolate BI compatibility in one asset.

**Benefits:** one definition per claim; understandable review path; existing filenames and compatibility can be preserved; implementation can be phased and mutation-tested.

**Costs:** requires deliberate migration of clauses, trace metadata, phase contracts, templates, validators, and BI adapters. A transition release must dual-read 2.6.0 artifacts.

**Decision:** recommended. It implements every Owner-approved direction without inventing a generator platform or a second state system.

### Option C — schema-first generated method distribution

Define the entire method in a machine model and generate SPEC, SKILL, README, references, contracts, and BI mappings.

**Benefits:** strongest byte-level consistency and lowest manual projection drift.

**Costs:** the generator becomes another method kernel, makes prose review harder, introduces tooling authority, and risks optimizing for generation rather than Owner comprehension. It is too large for a consolidation release.

**Decision:** rejected for 2.7.0. Narrow table generation may be used later only where a contract already owns the data.

## 7. Target authority architecture

### 7.1 Authority chain

| Layer | Sole responsibility | May define normative meaning? | Must not do |
|---|---|---:|---|
| Owner decisions | product direction, exceptions, approvals | yes | be inferred by AI |
| `CONSTITUTION.md` | immutable principles, Owner rights, method boundary | yes, constitutional only | restate lifecycle procedures, template fields, BI implementation |
| `SPEC.md` | complete LCCoding semantic rules | yes, sole full semantic authority | copy lower-method internals or runtime mechanisms |
| `contracts/` and schemas | machine shape, enumerations, gate relationships | mechanical authority only | introduce semantics absent from SPEC clauses |
| `templates/` | instances of contracts | no | invent options, gates, or duties |
| `lc-coding/SKILL.md` | concise execution entry and ordered operator guidance | no | become a second specification |
| README files | product overview, orientation, links, install/validate entry | no | carry detailed method law |
| `references/` | focused explanations, examples, rationale referenced by SPEC | no independent authority | add a new requirement or override a clause |
| validators/tests | prove consistency, behavior, and failure boundaries | no | accept keyword presence as semantic proof |
| BI documentation/code | BI product, projection, implementation, and release within separated scopes | no method authority | become project status or runtime control |
| historical designs | preserved decision history | no | appear in the current authority chain |

`FILE_HASHES.json` proves tracked-byte integrity. It does not grant semantic authority.

### 7.2 Stable clause identity

SPEC receives stable semantic clause IDs. The exact numbering is assigned during implementation, following these namespaces:

| Namespace | Subject |
|---|---|
| `LC-AUTH-*` | Owner/AI authority and platform boundary |
| `LC-PHASE-*` | phase ranges and gates |
| `LC-FORM-*` | Product Formation and Product Baseline |
| `LC-INTEG-*` | Feature Slice and Real Product Integration |
| `LC-RUN-*` | Run calling and return contract |
| `LC-VERIFY-*` | D0–D3 and evidence reuse |
| `LC-ACCEPT-*` | Loop and Post-Security Owner Acceptance |
| `LC-SEC-*` | vulnerability closure and invalidation |
| `LC-DELIVERY-*` | delivery decision and protection |
| `LC-BI-*` | built-in BI method boundary |
| `LC-COMPAT-*` | compatibility and migration |

IDs remain stable when wording improves. A semantic replacement supersedes an ID through migration metadata instead of silently reusing it for different meaning.

### 7.3 Projection trace contract

Every active projection section declares its source clause IDs. JSON contracts include a `normative_clause_refs` field where their existing schema permits metadata; Markdown projections use a compact `Source clauses:` line at section level. Templates cite their governing contract ID and clauses once at the top.

Mechanical checks require:

1. every source clause exists and is current;
2. no projection cites a superseded clause without a compatibility marker;
3. every contract semantic field maps to at least one SPEC clause;
4. no projection introduces a gate, phase, authority, state, or normative modal without a source;
5. links resolve in both directions from SPEC to topic and topic to SPEC.

This trace is metadata, not a second claim registry.

## 8. Authoritative phase model

### 8.1 Phase table

| Human phase | Compatibility ID | Entry condition | Included lifecycle work | Exit condition |
|---|---|---|---|---|
| Initial / 初始 | `INITIAL` | ready Owner proposal input | Proposal Readiness; new/existing Project Initialization | existing `INITIAL_READY` |
| Product Formation / 产品形成 | `PRODUCT_FORMATION` | `INITIAL_READY` | Calabash Draft; Product Simulation foundation; separately real/runnable Workflow, UI, and peer Simulation; Mandatory Calabash Upgrade; Product Baseline | existing Product Baseline Handoff is mechanically validated and accepted |
| Real Product Integration / 真实产品集成 | `ENGINEERING_RUNS` | existing Product Baseline Handoff is mechanically validated and accepted | Feature Slice; execution coverage preflight; first proving path when needed; UI-locked real API/MCP/state/data/side-effect/UI integration; integration evidence and per-Run Owner receipts | compatibility aggregate `ALL_REQUIRED_RUNS_ACCEPTED`, scoped only to required Phase-3 integration work |
| Delivery Preparation / 交付准备 | `DELIVERY_PREPARATION` | `ALL_REQUIRED_RUNS_ACCEPTED` | centralized audit, remediation, independent re-audit, vulnerability closure, Post-Security Owner Acceptance, delivery Q&A, package governance | existing `DELIVERY_READY` |

No new gate ID, schema field, or BI gate is introduced for this boundary. The existing `product_baseline` status plus a mechanically valid, accepted Product Baseline Handoff directly establish Product Formation completion and Phase-3 admission. `CALABASH_UPGRADE_READY` ceases to be the Product Formation exit; during migration it remains readable only as 2.6.0 compatibility evidence for readiness to begin Mandatory Calabash Upgrade.

### 8.2 Feature Slice boundary

Feature Slice is the first lifecycle work in Real Product Integration. Entering the phase requires Product Baseline readiness. A Slice then defines one actor-visible product claim. Execution Coverage Preflight is performed after the Slice exists and before a bounded integration Run is dispatched; it is not the phase-entry gate.

### 8.3 Real-integration proof

A Phase-3 integration claim is true only when evidence covers the same capability across:

```text
UI action
→ real API or MCP entry
→ real Workflow rules
→ real state / data / side effect
→ visible UI result
↔ applicable Product Simulation scenario and failure/recovery behavior
```

A picture, mock, stub, scripted visual state, or disconnected demonstration may be Product Formation evidence. It cannot satisfy Real Product Integration, D0–D3, or delivery readiness.

When a change touches one link, Impact Analysis identifies the affected connected links and evidence. Unaffected links are cited and reused rather than mechanically regenerated.

### 8.4 Compatibility ID policy

In 2.7.0:

- persisted/API ID remains `ENGINEERING_RUNS`;
- English display is `REAL_PRODUCT_INTEGRATION` or “Real Product Integration”;
- Chinese display is `真实产品集成`;
- “Engineering Runs” appears only in explicit compatibility explanations, schemas, migrations, or historical evidence.

A future machine-ID migration is allowed only in a separately approved compatibility release after status schema, validators, templates, BI adapters, project manifests, and installed skills can dual-read both IDs. 2.7.0 does not perform that migration.

## 10. Run and execution-method contract

### 10.1 Every Run is called by a phase

Every Run-start record contains exactly these semantic groups:

1. Run identity and calling phase ID;
2. phase-owned objective;
3. calling phase authority and clause/contract references;
4. frozen Run scope and exclusions;
5. selected registered method identity, version, hash, and interface reference;
6. phase-appropriate inputs and evidence prerequisites;
7. evidence return target in the calling phase;
8. D0–D3 and Loop Owner Acceptance condition;
9. risk/depth decision;
10. readiness result `READY` or `BLOCKED`.

Product Baseline, Feature Slice, UI identity, Integration Baseline, and proving-route fields are required only when applicable to a Real Product Integration Run. Other phases supply their own authority; they never fabricate Feature Slice or Calabash evidence.

### 10.2 `RUN-HANDOFF.md` becomes Run-start input

The path is retained for 2.6 compatibility, but its artifact role becomes `RUN_START_CONTRACT`. It must not contain:

- D3 receipt;
- final candidate verdict;
- Owner result;
- acceptance timestamp;
- gap closure result.

Those are unknown at Run start.

### 10.3 `LOOP-OWNER-ACCEPTANCE.md` remains the end receipt

Every normal Run in any phase ends with:

```text
D3 PASS
→ LOOP_OWNER_ACCEPTANCE_READY
→ Loop Owner Acceptance
→ evidence returned to the calling phase
```

The end receipt contains the exact Run-start reference, final candidate, D3 receipt, Owner result, gap lineage, and evidence return. Run acceptance does not itself pass the calling phase gate.

### 10.4 Aggregate gate scope

`ALL_REQUIRED_RUNS_ACCEPTED` retains its machine ID but its full semantic name is “all required Real Product Integration Runs accepted.” It aggregates only Runs explicitly listed by the Phase-3 Required Runs set for the accepted integration candidate.

It does not count:

- Initial intake/repair Runs;
- Product Formation Workflow/UI/Simulation/Calabash Runs;
- Delivery Preparation security, packaging, or delivery Runs;
- optional or superseded Runs;
- a Run whose evidence was invalidated.

### 10.5 Minimal execution-method registry

No new registry subsystem is introduced. The existing Canonical Manifest becomes the sole project registry source for eligible methods. Its execution-method entries must provide only:

- method ID;
- version and exact hash;
- canonical contract reference;
- Run evidence/D0–D3 mapping;
- Loop Owner Acceptance mapping;
- compatible `LCCODING_LOOP_CONTROL` binding requirement;
- compatibility result.

The fixed legacy `slk`, `clk`, and `glk` fields remain readable during migration. New projects use the generic execution-method collection. LCCoding does not copy method topology, roles, retries, Chains, Stages, or graphs.

## 11. Calabash boundary

LCCoding 2.7.0 consumes Calabash 2.5.0 through a narrow definition handoff:

- Definition Baseline ID/version/hash and cited clauses;
- applicable Snake IDs, guards, dispositions, and evidence references;
- applicable Scorpion IDs, mechanical hard blocks, status, and evidence references;
- meaning-change and invalidation rules;
- Mandatory Upgrade result and Owner authority.

LCCoding does not copy Minimum/Full construction procedures, Theme interviews, layer definitions, feedback intake, or Calabash validators.

Before any 2.7.0 formal release or global Skill deployment, implementation must mechanically verify the exact Calabash 2.5 canonical identity actually adopted by the compatibility baseline. This design observed the local canonical version but does not assert that any particular Calabash tag or GitHub Release is formally published.

Meaning-changing work requires an applicable Calabash Definition Baseline basis or a governed route to update it. Strictly meaning-neutral engineering work cites its phase contract and impact result and must not fabricate a Calabash baseline. A Snake `OPEN` or Scorpion `HIT` blocks the affected definition/work according to Calabash authority.

Mandatory Calabash Upgrade and the accepted Definition Baseline occur inside Product Formation before LCCoding freezes Product Baseline. The two baselines remain distinct: one fixes meaning; the other fixes realized product identity.

## 12. UI, Workflow, Simulation, and product mainline

### 12.1 Repository and subtree model

One total project Git/GitHub repository is the default product repository. Realized UI, Workflow, and Product Simulation units are peer logical paths inside that repository, each recording safe relative path, component version, and deterministic content hash.

Git worktrees are optional construction isolation. They are never product structure, subtree identity, or baseline identity.

### 12.2 Workflow interfaces

Every implemented CORE Workflow and every implemented EXTRA Workflow exposes API and MCP contracts backed by the same real capability, rules, state, side effects, and evidence. The requirement does not imply duplicate implementations, microservices, or an LCCoding runtime.

Unimplemented EXTRA is a registry claim only. It has no empty subtree and no API/MCP capability claim. CORE cannot be downgraded to EXTRA to pass Product Baseline without a Calabash definition change and Owner confirmation.

### 12.3 Primary product mainline

The Owner confirms one relation linking at least one peer Product Simulation, one CORE Workflow, and one UI. It selects the first proving route and priority only. Other CORE obligations remain Product Baseline and completion requirements.

### 12.4 One-way UI lock

After Product Baseline, applicable UI is locked against autonomous change by Workflow, Simulation, execution methods, Agents, runtimes, or automation. The Owner may initiate or explicitly approve change. A legal change uses the existing Baseline Change Request, creates a distinct project commit and updated identity, records impact, and re-verifies affected evidence. The system never silently overwrites or automatically restores Owner material.

## 13. Shared Loop Control and transitional binding

`LCCODING_LOOP_CONTROL` owns only policy and evidence common to compatible Loop methods. It does not own execution topology and LCCoding does not perform runtime operations.

### 13.1 Distinct heartbeat concepts

| Term | Cardinality and lifetime | Purpose |
|---|---|---|
| `RUN_PATROL_HEARTBEAT` | at most one active heartbeat for one active Run; removed at terminal closure | periodic non-technical liveness/policy observation |
| `CHECKER_WAKE_HEARTBEAT` | one temporary wake-escalation artifact per delivery/wake incident; removed after ACK or terminal fallback | wake a bound Checker after earlier levels fail |

They cannot share an ID, lifetime rule, count, or evidence claim.

### 13.2 Model policy

The shared contract defines capability classes and records the actual binding:

- fastest suitable non-technical inspection model for Patrol; current GPT example: Luna + `xhigh`;
- ordinary technical roles: Terra + `xhigh`;
- difficult correction, root-cause diagnosis, or complex rework: Sol + `xhigh`;
- `ultra` requires separate item-specific Owner authorization;
- GPT 5.5 and lower are prohibited for current formal work.

LCCoding remains Agent-platform-independent by governing capability and evidence, while examples make the current expected GPT binding unambiguous.

### 13.3 Progress ownership

- Worker reports delivered CELL `x/y` to Checker.
- Checker reports accepted CELL `x/y` to Supervisor.
- Supervisor reports GO/Level/Run scope and material state.
- Patrol reports no engineering progress.

### 13.4 Transitional adoption

The three existing methods retain their verified local wake, patrol, progress, capacity, Pin, and model controls until all of these are true for that method:

1. it cites the exact shared contract ID/version/hash;
2. it maps method-specific fields without weakening common rules;
3. a trusted runtime emits current, mechanically verifiable attestations;
4. positive and negative conformance tests pass against real runtime evidence;
5. historical receipts remain readable;
6. the method's own Owner-approved release explicitly retires duplicated engine behavior.

Until then, binding is transitional and local controls remain active. LCCoding does not delete or execute those controls. After transition, method repositories retain only topology-specific mapping and validation, not copies of the shared policy text.

## 14. Security-closure invalidation

Vulnerability Closure and Post-Security Owner Acceptance are valid only for the exact candidate identity and covered attack surfaces named by their receipts.

If any Delivery Preparation Run after `VULNERABILITY_CLOSED` or after `POST_SECURITY_OWNER_ACCEPTED` changes product behavior, dependencies, configuration, privilege, data handling, API exposure, client exposure, installer/runtime behavior, or another declared security surface:

1. Impact Analysis identifies the changed candidate and affected surfaces;
2. `vulnerability_closure`, `post_security_owner_acceptance`, and `DELIVERY_READY` become `INVALID` for the changed candidate in authoritative `status.json`;
3. the prior receipts remain immutable evidence for the prior candidate;
4. affected engineering evidence is invalidated, while unaffected evidence is reused;
5. a fresh independent security re-audit covers the delta and any transitively affected surface;
6. a new Vulnerability Closure Receipt binds the new candidate;
7. focused Post-Security Owner Acceptance is repeated for affected product surfaces and critical smoke;
8. Delivery remains blocked until the new candidate satisfies closure, Owner acceptance, delivery Q&A, and package protection.

A change proven meaning-neutral and security-surface-neutral may preserve closure only when an Impact Analysis explicitly records the unchanged candidate/security identity or an evidence-equivalent packaging transformation. Silence never preserves closure.

This uses existing authoritative status and receipt evidence. It adds no status source or security runtime.

### 15.2 Single method-compatibility asset

The existing `lc-coding/bi/release/loop-contract-identities.json` evolves in place and remains the one active BI method-compatibility source. 2.7.0 does not create a second compatibility file under `lc-coding/bi/contracts/`, and it does not retain an old and new identity asset side by side. The existing path is the smallest migration because production release verification already consumes it.

Its schema expands, without changing its single-source role, to cover:

- supported LCCoding status schema versions;
- supported SLK, CLK, GLK, and compatible method adapter versions;
- exact manifest/schema/template or contract identities;
- adapter schema kind and normalization mapping;
- current versus supported-legacy status;
- minimum BI/LCCoding version that understands each entry.

Rust embeds or reads generated constants from this exact asset. PowerShell release verification continues reading the same path. Documentation cites it without duplicating version literals. All Rust constants, release checks, documentation assertions, and adapter tests migrate in one batch; only after every consumer reads this path may duplicated literals be deleted. Active source and release scripts must contain no independent SLK/CLK/GLK version constants. Historical migrations and test fixtures may retain old versions only when explicitly marked historical/test-only.

Implementation must assess formally published identities before changing compatibility. It must not simply replace SLK/CLK 2.5.0 with 2.6.0 and strand existing project evidence; compatible legacy and current adapters may coexist when mechanically proven.

## 18. Compatibility and migration strategy

### 18.1 Repository release migration

2.7.0 introduces a normal versioned migration from 2.6.0. It does not rewrite 2.6.0 tags, releases, migration documents, or historical project evidence.

### 18.2 Project-status migration

The migrator reads 2.6.0 evidence and reclassifies phase position without fabricating completion:

| 2.6.0 evidence | 2.7.0 phase result |
|---|---|
| before Calabash Draft | `INITIAL` |
| Calabash Draft/product ends/Mandatory Upgrade incomplete | `PRODUCT_FORMATION` |
| Mandatory Upgrade complete but Product Baseline not mechanically valid | `PRODUCT_FORMATION`, blocked |
| Product Baseline valid and Feature Slice/integration not complete | compatibility ID `ENGINEERING_RUNS`, display Real Product Integration |
| all required Phase-3 integration Runs accepted | `DELIVERY_PREPARATION` entry eligible |

Existing accepted receipts remain evidence. A phase reclassification does not revoke them unless their underlying claim or candidate is invalid.

### 18.3 Gate migration

- 2.6 `CALABASH_UPGRADE_READY` remains readable as historical/internal readiness evidence.
- 2.7 uses the existing `product_baseline` status and mechanically valid, accepted Product Baseline Handoff directly as Product Formation exit evidence; it adds no gate ID or status field.
- `FEATURE_SLICE_EXECUTION_COVERAGE_PASS` remains a per-Slice/per-integration-Run admission gate inside Phase 3.
- `ALL_REQUIRED_RUNS_ACCEPTED` retains its ID and narrows explicitly to the required Phase-3 integration set.
- `DELIVERY_READY` remains the final phase exit and becomes invalid if security/Owner evidence is stale for the current candidate.

### 18.4 BI migration

BI keeps the four phase IDs and 21-step order but changes the display grouping for 2.7.0 status:

- Mandatory Calabash Upgrade and Product Baseline display under Product Formation;
- Feature Slice is the first Real Product Integration step;
- `ENGINEERING_RUNS` is rendered only through the Real Product Integration label;
- 2.6.0 status remains readable through a version-specific compatibility mapping;
- no fixture, raw path, status write, or runtime control is introduced.

### 18.5 Rollback

Before release, rollback is a normal feature-branch revert. After release, 2.6.0 remains immutable and available. Project migration is copy-on-write with preserved source artifacts and receipts; failed 2.7.0 validation leaves the project on its prior compatible version. No rollback rewrites a frozen Product or Calabash Baseline.

## 20. Test and validation strategy

### 20.1 Authority graph

- parse every SPEC clause ID and projection `Source clauses` declaration;
- reject missing, duplicate, superseded, cyclic, or orphan references;
- reject an active historical design in the normative manifest;
- prove README/SKILL/reference sections do not introduce unreferenced phase, gate, state, or authority claims.

### 20.2 Phase semantics

Positive fixture:

- Product Formation contains Mandatory Calabash Upgrade and Product Baseline;
- Real Product Integration starts at Feature Slice;
- Delivery Preparation begins only after accepted required integration work.

Negative mutations:

- put Mandatory Upgrade/Product Baseline back under `ENGINEERING_RUNS`;
- place Feature Slice before Product Baseline;
- use Execution Coverage Preflight as the phase-entry gate;
- invent a separate Product Baseline phase-gate ID instead of using the validated/accepted Handoff directly;
- display “Engineering Runs” as the human phase name;
- count an Initial or Delivery Run in `ALL_REQUIRED_RUNS_ACCEPTED`.

Each mutation must fail through parsed contract relationships, not keyword absence.

### 20.3 Run contract boundary

- Run Handoff validates only start-known fields and rejects D3/Owner-result fields;
- Loop Owner Acceptance requires exact Run-start identity and D3 evidence;
- acceptance returns evidence but does not mutate a phase gate automatically;
- another registered method fails unless its Canonical Manifest entry supplies the minimal interface.

### 20.4 Calabash and baseline semantics

- meaning-changing Run requires valid Definition Baseline clauses and applicable Snake/Scorpion references;
- meaning-neutral work passes without a fabricated Calabash baseline when impact evidence proves neutrality;
- a Snake `OPEN` or Scorpion `HIT` blocks affected work;
- Product, Integration, Definition, and Method Baseline identities cannot substitute for one another.

### 20.5 Product integration

- positive real chain proves UI/API-or-MCP/Workflow/state-side-effect/visible UI/Simulation scenario;
- mock-only, image-only, disconnected, wrong-candidate, stale UI, or missing side-effect cases fail;
- Workflow API/MCP contracts map to the same capability;
- unimplemented EXTRA has no capability/interface claim;
- Primary mainline does not remove other CORE obligations.

### 20.6 Loop Control transition

- distinguish Run Patrol and Checker Wake heartbeats by cardinality/lifetime;
- reject stale/mismatched runtime attestation;
- retain local method control until all transition gates pass;
- validate model capability class, actual model, effort, Owner Ultra authorization, and minimum floor;
- verify progress ownership without assigning engineering progress to Patrol.

### 20.7 Security invalidation

- candidate/security-surface change after closure sets current closure, Post-Security acceptance, and Delivery readiness invalid;
- prior receipts remain immutable;
- unaffected evidence is reused;
- no new delivery occurs before re-audit, new closure, and re-acceptance;
- a proven neutral change can preserve closure only with explicit impact evidence.

### 20.8 BI compatibility

- `lc-coding/bi/release/loop-contract-identities.json` is the only active source of lower-method/status compatibility identities, and no parallel asset exists;
- source scan rejects independent active literals in Rust, PowerShell, and current docs;
- 2.6 and 2.7 fixtures project their correct phase grouping;
- four phases, 21 steps, reports, 300×480 UI, bilingual behavior, read-only boundary, and security controls remain;
- production graph contains no test fixture dependency.

### 20.9 Full release gates

- JSON/Markdown/reference resolution;
- schema/contract/template/example/validator consistency;
- project validator positive and adversarial fixtures;
- all Python tests and repository/hash integrity;
- React typecheck/DOM/accessibility/visual tests;
- Rust normal/release/security/project immutability tests;
- Windows package/provenance/install/uninstall smoke when BI surfaces change;
- migration from 2.6.0 with no source artifact loss;
- exact diff/whitespace/secret/forbidden-scope scan.

## 21. Success criteria

2.7.0 succeeds when all of these are evidenced:

1. every current normative claim has exactly one authoritative SPEC or Constitution definition;
2. every contract/template/projection claim resolves mechanically to a current clause;
3. no active phase surface disagrees about Product Formation or Real Product Integration boundaries;
4. Product Formation exits directly on existing Product Baseline status plus mechanically valid/accepted Handoff evidence, with no new gate ID, schema field, or BI gate;
5. `ENGINEERING_RUNS` has an explicit compatibility-only explanation everywhere it appears to humans;
6. Run-start and Run-end artifacts have disjoint time-appropriate fields;
7. cross-phase Runs return evidence without auto-advancing phases;
8. `ALL_REQUIRED_RUNS_ACCEPTED` cannot accept a non-Phase-3 Run;
9. Calabash handoff references Definition Baseline/Snake/Scorpion without copying Calabash construction internals;
10. the four baseline kinds and two Simulation/Pin meanings are unambiguous;
11. the existing BI identity asset is the sole active source of all method/status compatibility identities;
12. historical designs are clearly non-normative and absent from the current authority graph;
13. the main entry surfaces are materially shorter and one-hop navigable, with no independent long-form rule blocks; exact deleted line count is reported but is not a pass criterion;
14. tests prove positive and negative semantics, not merely keyword presence;
15. the BI implementation, dependencies, security tests, and release safeguards remain intact;
16. existing 2.6.0 projects and evidence migrate without reset, silent completion, or loss;
17. the released and globally installed Skill identities match only after approved deployment.

## 22. Version rationale

`2.7.0` is the correct target because this work changes the normative information architecture, phase boundary contract, status migration, Run contract roles, BI compatibility model, and security invalidation semantics while preserving the product-development mainline and backward-reading compatibility.

It is larger than a patch and smaller than a method replacement. It does not overwrite `2.6.0`; it requires a new migration, tag, release, and acceptance cycle. Owner approval is already required and recorded for a `1.0.1+` promotion.

## 23. Risks and controls

| Risk | Control |
|---|---|

## 24. Rollback and recovery

- This design commit changes no active method or runtime behavior.
- Implementation occurs only on an isolated feature branch.
- Every migration batch is independently reviewable and revertible before release.
- `2.6.0` tags, releases, artifacts, and project evidence remain immutable.
- A failed project migration leaves the prior artifacts untouched and returns a blocked report.
- A failed BI compatibility or packaging gate blocks 2.7.0 release; it never overwrites an installed or published prior version.
- Lower-method local controls remain until their own approved transitions, so rollback never depends on an absent shared runtime.
