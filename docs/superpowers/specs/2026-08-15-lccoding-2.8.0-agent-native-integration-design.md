# LCCoding 2.8.0 Agent-Native Integration Design

**Status:** Owner decisions are approved; this written design awaits independent Supervisor review.

**Base:** LCCoding `2.7.0`, commit `7bc16db388cd2f8ff44e69b75a4de610d9845942`.

**Target:** LCCoding `2.8.0`.

**Document role:** historical design provenance only. It does not modify the current method, deploy an Agent, alter LCagent, authorize a Runtime, change a project, release software, or create current evidence. `SPEC.md` remains the sole semantic authority after, and only after, accepted implementation transfers these decisions into active clauses and mechanical contracts.

## 1. Problem statement

LCCoding 2.7 establishes four lifecycle phases, a Simulation-first Product Formation, Feature Slice as the Real Product Integration progress unit, exact evidence identity, independent Verification, Owner acceptance, security invalidation, protected Delivery, a read-only BI, and a Runtime-neutral execution-method boundary. It does not yet define how an Agent-native product is formed, isolated, integrated, degraded, secured, projected, and migrated without confusing product Agents with construction Agents or turning LCCoding into an Agent Runtime.

That omission creates five risks:

1. A construction Supervisor, Worker, or Checker can be mistaken for a delivered Product Agent.
2. A Product Agent and an Operations Agent can be collapsed into one process with shared private memory and credentials.
3. A dashboard or chatbot can be presented as Operations integration without a controlled maintenance action path.
4. Multiple experimental backends can survive Product Formation without a final production authority/topology decision.
5. A 2.7 project can be relabeled 2.8 without proving the required Operations Agent, Runtime Adapter, isolation, security, and migration evidence.

LCCoding 2.8 closes these gaps while retaining the existing lifecycle, Feature Slice, Owner authority, Calabash boundary, execution-method axis, status authority, security gates, and Delivery protections.

## 2. Decision summary

The 2.8 architecture is:

```text
Owner authority
→ Calabash product definition and Agent applicability
→ LCCoding construction of runtime-neutral Agent configuration and product capability
→ independent Verification and Owner acceptance
→ authorized Runtime Adapter loads the exact accepted configuration
→ Feature Slice proves PRODUCT or OPERATIONS behavior on the final production topology
→ existing security closure, Post-Security Owner Acceptance, and Delivery protection
```

The lifecycle remains exactly four phases:

```text
INITIAL
→ PRODUCT_FORMATION
→ REAL_PRODUCT_INTEGRATION
→ DELIVERY_PREPARATION
```

For 2.8 new-write artifacts, the third-phase machine ID is exactly `REAL_PRODUCT_INTEGRATION`. `ENGINEERING_RUNS` remains read-only compatibility input for exact 2.6/2.7 schemas. It is never written by a 2.8 project. Migration is copy-on-write and does not promote old evidence to new completion.

SLK, CLK, GLK, and compatible registered execution methods remain a horizontal, per-Run execution axis callable from any phase. They are not Agent types, lifecycle nodes, Runtime Adapters, or phase-advance authorities.

## 3. Goals

1. Distinguish Construction Agents, Product Agents, and Operations Agents mechanically and semantically.
2. Require one real Operations Agent integration for every 2.8 project without making that Agent a default core-business single point of failure.
3. Let Calabash decide whether a Product Agent applies and whether it is CORE product capability.
4. Define one platform-neutral Agent Configuration Baseline and one exact Runtime Adapter attestation path without implementing a Runtime.
5. Prove independent Product Agent and Operations Agent trust boundaries when both exist.
6. Require a final production execution topology without requiring a monolithic backend.
7. Extend the existing Feature Slice unit with exact `PRODUCT` and `OPERATIONS` proof routes.
8. Add Agent-specific security, fallback, replacement, audit, and Delivery evidence without weakening existing gates.
9. Move the active third-phase machine ID to `REAL_PRODUCT_INTEGRATION` for 2.8 new writes while preserving strict 2.6/2.7 reads.
10. Keep the built-in BI read-only and visually stable while projecting only a minimal sanitized Agent-native summary.

## 4. Non-goals

- No fifth lifecycle phase, Agent phase, Agent gate, second lifecycle axis, or new phase-exit gate.
- No Agent Runtime, session engine, memory engine, vector database, model router, process manager, action executor, orchestration service, or second status authority inside LCCoding.
- No mandatory LCagent, OpenAI, SDK, model, embedding provider, vector store, operating system, or deployment topology.
- No replacement or redefinition of Calabash, Scorpion, SLK, CLK, GLK, or another compatible execution method.
- No mandatory single Product Backend, Core service, monolith, microservice layout, or physical service merge.
- No parallel progress system beside Feature Slice.
- No Operations dashboard that claims integration without a deterministic action/verification/rollback/audit path.
- No default autonomous operations, self-authorization, self-modification, secret storage in Git, or implicit Owner approval.
- No BI control plane, Agent console, raw evidence browser, session viewer, prompt editor, secret viewer, or visual redesign.
- No deployment of a real Agent or LCagent as part of the method implementation. A fake or reference adapter proves contracts; real Runtime deployment requires later Owner authorization.

## 5. Locked terminology and Agent classes

### 5.1 Construction Agent

A **Construction Agent** is an engineering participant such as Supervisor, Worker, Checker, independent Verifier, Auditor, or acceptance preparer. It builds or verifies the product under the existing LCCoding Run and Owner-authority contracts. It is never a delivered Product Agent or Operations Agent merely because it uses an Agent platform, MCP, tools, memory, or a named role.

Construction Agent identities and runtime controls remain outside product Agent configuration. Their evidence may prove construction, but their sessions, prompts, credentials, and memories cannot be reused as delivered product-Agent state.

### 5.2 Product Agent

A **Product Agent** participates in the user's business behavior. Calabash decides exact applicability, actors, authority, capabilities, failure/degradation behavior, and whether the Agent is CORE or EXTRA. If it is CORE, Product Formation must implement it as real, runnable product capability, expose the same underlying Workflow capability through governed API/MCP interfaces, cover it in Simulation, and include it in Product Baseline. If it is not applicable, the exact disposition is `NOT_APPLICABLE` with Calabash evidence; a missing or implicit disposition is invalid.

A Product Agent may manage only Calabash-authorized user preferences and its own bounded session memory. It cannot alter root configuration, its permission ceiling, isolation boundary, credentials, Scorpion blocks, Kill Switch, or Operations Agent state.

### 5.3 Operations Agent

An **Operations Agent** is a required delivered logical Agent for every 2.8 project. It observes and assists with product operation and maintenance through a governed action path. It is not a passive dashboard, not a construction Patrol, and not autonomous by default.

Its minimum real path is:

```text
observe
→ diagnose
→ propose
→ Owner authorization or exact Calabash pre-authorization
→ deterministic action
→ verify
→ rollback when required
→ append-only audit evidence
```

It reads at least health, version, configuration, logs, and events; explains anomalies and affected product behavior; produces a maintenance proposal with risk and rollback; invokes only cataloged deterministic actions after the required authority; verifies postconditions; rolls back when the action contract requires it; and records audit evidence.

Data deletion, permission changes, release, upgrade, database migration, credential changes, Kill Switch changes, and irreversible actions require explicit Owner approval by default. Calabash may pre-authorize only individually identified low-risk actions with bounded inputs, targets, effects, duration, verification, rollback, and audit. Silence, a broad role, or a risk label alone is not authorization.

### 5.4 Product and Operations Agents together

When both apply, they are two independent logical Agents. A single Agent switching roles, prompts, namespaces, or “memory modes” does not satisfy the design. Shared model binaries or a shared Runtime implementation are allowed only when the required isolation result remains mechanically verifiable.

## 6. Four-phase semantics

### 6.1 `INITIAL`

Initial retains Proposal Readiness and Project Initialization. For 2.8 it additionally records, without implementing:

- Product Agent applicability decision basis or the exact future Calabash decision route;
- required Operations Agent purpose and prohibited authority;
- root configuration owner;
- private-memory and credential boundaries;
- fallback/degradation expectations;
- required Kill Switch ownership;
- candidate Runtime capability requirements without selecting a mandatory vendor.

These are initialization inputs, not a new gate. `INITIAL_READY` remains the only exit gate.

### 6.2 `PRODUCT_FORMATION`

Product Formation remains Simulation-first and retains real Workflow, UI, CORE/EXTRA, API+MCP, Mandatory Calabash Upgrade, and Product Baseline.

During formation:

1. Calabash resolves Product Agent applicability, capability, authority, and CORE/EXTRA classification.
2. A CORE Product Agent is implemented as real product capability before Product Baseline; an EXTRA Product Agent follows existing EXTRA rules.
3. The project creates runtime-neutral Policy and Action Catalog records, configuration identity, memory/credential boundaries, telemetry/audit requirements, fallback behavior, and Adapter capability requirements for each applicable product Agent and for the required Operations Agent.
4. Simulation covers the same Agent-visible state, abnormal conditions, authorization boundaries, failure, degradation, recovery, and Kill Switch behavior.
5. Product Baseline freezes the realized Product Agent capability when applicable and freezes prepared Operations Agent configuration without claiming Operations integration.

Product Formation does not have to connect the Operations Agent to the production system. That proof belongs to the third phase.

### 6.3 `REAL_PRODUCT_INTEGRATION`

The 2.8 new-write machine ID and human meaning are both `REAL_PRODUCT_INTEGRATION` (Chinese: `真实产品集成`). The phase begins with Feature Slice after accepted Product Baseline evidence.

It must:

- select, compose, federate, or retire every relevant Product Formation execution backend;
- freeze the final production execution topology and logical authorities;
- connect the required Operations Agent through an authorized Runtime Adapter;
- connect an applicable Product Agent without merging it with the Operations Agent;
- prove `PRODUCT` and required `OPERATIONS` Feature Slices;
- prove isolation, authorization, deterministic actions, verification, rollback, audit, fallback, and recovery;
- retain UI one-way Owner lock, Workflow controlled mutability, Simulation versioned mutability, and Calabash impact trace;
- end required Runs through existing D0–D3 and per-Run Owner acceptance.

No new phase gate is added. The existing required-Run aggregate remains the phase exit evidence, now scoped to required 2.8 Real Product Integration Slices on the accepted candidate.

### 6.4 `DELIVERY_PREPARATION`

Delivery Preparation retains centralized security closure, remediation, independent re-audit, Post-Security Owner Acceptance, Delivery Q&A, package guard, and `DELIVERY_READY`. It adds covered evidence for Agent-specific attack and failure surfaces but creates no parallel security or delivery gate.

## 7. Semantic authority and mechanical artifact model

The implemented method keeps `SPEC.md` as sole semantic authority. The active clause set will add a small Agent-native family rather than copying rules across entry documents:

- `LC-AGENT-001`: Agent classes, applicability, and required Operations Agent;
- `LC-AGENT-002`: Agent Configuration Baseline, authority flow, and Runtime neutrality;
- `LC-AGENT-003`: dual-Agent isolation, communication, authorization, and protected controls;
- `LC-INTEG-004`: final production topology plus `PRODUCT`/`OPERATIONS` Slice proof;
- `LC-SEC-003`: Agent security, degradation, replacement, and Delivery evidence.

The following project artifacts mechanically instantiate those clauses:

| Artifact | Responsibility | Explicitly does not own |
|---|---|---|
| `.lccoding/AGENT-CONFIGURATION-BASELINE.json` | exact Agent applicability, IDs, runtime-neutral Policy/Action Catalog identities, memory/credential boundaries, root authority, fallback and accepted configuration hash | Runtime state, sessions, secrets, live memory |
| `.lccoding/AGENT-ACTION-CATALOG.json` | deterministic action IDs, risk, authority requirement, bounded inputs/targets, postconditions, rollback, and audit requirements | Agent reasoning, credentials, free-form shell authority |
| `.lccoding/PRODUCTION-EXECUTION-TOPOLOGY.json` | exact candidate, services/backends and disposition, behavior/state/data authority, permission/consistency/recovery/calling boundaries, Agent routes | physical monolith requirement, runtime session state |
| `.lccoding/RUNTIME-ADAPTER-ATTESTATION.json` | exact Adapter identity and digest, loaded configuration/topology, capabilities, isolation, credential separation, telemetry, fallback, Kill Switch and current verification evidence | Runtime implementation or automatic deployment |
| existing Feature Slice / Integration / Verification artifacts | one `PRODUCT` or `OPERATIONS` claim, exact route, evidence and acceptance | parallel program, Agent state store, extra gate |
| existing `status.json` | authoritative progress and exact pointers to current accepted artifacts | raw evidence, prompts, secrets, sessions, runtime state |

All JSON artifacts use strict UTF-8 closed objects, duplicate-key rejection, safe contained references, exact lowercase SHA-256 identity, non-generic IDs, candidate binding, and deny-unknown validation. Templates are not evidence. Validators are read-only.

## 8. Agent Configuration Baseline and configuration authority

The configuration flow is fixed:

```text
Owner decides
→ Calabash defines product meaning, Agent applicability, authority and Scorpion limits
→ LCCoding Construction Agents implement runtime-neutral configuration
→ independent Verification proves identity, behavior, isolation and fallback
→ Owner accepts the exact configuration candidate
→ authorized Runtime Adapter mechanically loads that exact identity
```

The baseline records two independent logical Agent slots:

- `operations_agent`: always `REQUIRED` for 2.8;
- `product_agent`: `APPLICABLE_CORE`, `APPLICABLE_EXTRA`, or `NOT_APPLICABLE` with exact Calabash evidence.

Each applicable slot records a distinct Agent ID; Policy ID/version/hash; Action Catalog ID/version/hash; prompt/config package ID/version/hash; private memory store and retriever identity; credential-set reference; encryption-key reference; audit stream identity; Kill Switch identity; fallback mode; allowed product-state interfaces; and Owner acceptance evidence. It records only identifiers, contained references, and digests—never secret material, tokens, raw prompts, raw memory, or credentials.

Root identity, permission ceiling, private-memory boundary, Scorpion constraints, credentials, encryption keys, audit policy, and Kill Switch are protected root configuration. No Agent may change them. Product Agents may change only individually permitted user preferences and their own bounded session memory. Operations Agents may propose a configuration delta, but protected root changes require exact Owner approval and the normal impact/re-verification route. No third configuration Agent is introduced.

## 9. Runtime neutrality and Adapter contract

LCCoding defines required capabilities and evidence, not implementation technology. LCagent is one Owner-preferred reference Runtime among potentially many; LCagent implementation remains in the LCagent project.

An Adapter is accepted only when it mechanically proves:

- exact Adapter ID/version/content digest and Runtime provider identity;
- exact loaded Agent Configuration Baseline and Production Topology identity;
- distinct logical Agent construction for Product and Operations slots;
- required session/context, private memory, retriever, credential, key, prompt-cache, Policy, Action Catalog, audit, and Kill Switch boundaries;
- no permission expansion, Agent merge, boundary weakening, or Scorpion override;
- deterministic Action Catalog invocation and authoritative authorization check;
- current telemetry, failure/degradation, rollback, audit, and Runtime-replacement behavior;
- independent positive and negative acceptance using a fake/reference Adapter without external secrets.

Runtime attestation is candidate-bound and time-bound. A safe-looking self-report, environment variable, vendor name, or `current=true` flag is insufficient. Replacement of the Runtime or Adapter is a material identity change unless Impact Analysis proves exact security/behavior equivalence under the existing evidence-neutral rule.

## 10. Dual-Agent trust boundary

### 10.1 Required isolation

Product and Operations Agents have independent:

- Agent ID;
- session and context;
- private memory store, vector index, and retriever;
- write credentials and encryption key;
- system prompt and prompt cache;
- API/MCP/tool credentials;
- Policy and Action Catalog;
- audit stream;
- Kill Switch.

The equality or aliasing of any required independent identity fails validation. Two namespaces in one writable store, one credential with two labels, one prompt with role switching, or one session with cleared history does not prove isolation.

### 10.2 Permitted sharing

The Agents may share a base model, inference Runtime implementation, read-only public assets, and authoritative product state exposed through governed interfaces. Shared authoritative product state is not Agent memory. Reads and writes follow each Agent's distinct permissions and are audited.

High-security projects may require separate processes, operating-system accounts, storage services, networks, or hardware keys. LCCoding requires mechanically verifiable isolation outcomes and Calabash-specific risk depth; it does not prescribe one deployment topology for every product.

### 10.3 Cross-Agent communication

Only typed, minimal, audited events may cross the boundary. Initial required types are `MAINTENANCE_REQUEST` and `SERVICE_STATUS_UPDATE`. Each event carries safe event ID, schema version, source Agent ID, target Agent ID, candidate identity, minimal payload classification, provenance evidence, redaction result, Policy decision, and timestamp.

Natural-language messages may convey user-visible context but cannot convey administrator authority, credentials, root configuration approval, or a memory dump. Every event is policy-checked and redacted before delivery. Private memory, raw sessions, unmanaged summaries, prompts, credentials, and prompt caches never cross.

Private memory from either Agent must not be used for online training or weight updates to a shared model. Governed offline improvement would require a separate Owner-approved product decision outside this design.

## 11. Operations Agent controlled-action path

The Operations Agent Action Catalog is closed and deterministic. Every action record includes:

```text
action_id
version and exact digest
risk class
allowed target identity and operation
typed input schema
preconditions
authorization mode
authorization evidence shape
deterministic executor/adapter operation
postconditions and verification
rollback operation and rollback trigger
audit event types
timeout and bounded retry policy
```

Authorization mode is one of:

- `OWNER_APPROVAL_REQUIRED`;
- `CALABASH_PREAUTHORIZED_BOUNDED`.

The second mode requires exact Calabash clause/evidence, bounded action identity, low-risk classification, permitted target/input range, expiry/currentness, verification, rollback, and audit. It cannot apply to data deletion, permissions, release, upgrade, database migration, credential/root configuration, Kill Switch, or irreversible actions.

The Agent proposes; the deterministic Adapter action executes. Free-form shell, arbitrary code generation/execution, dynamic tool discovery, or an Agent-authored action definition cannot substitute for a cataloged action. A failed verification invokes the cataloged rollback when safe; rollback failure becomes visible blocking evidence and routes to Owner-governed recovery.

## 12. Final production execution topology

Product Formation may produce multiple runnable backends, services, adapters, data stores, or experimental paths. Real Product Integration must assign each relevant candidate one disposition:

- `SELECT`: it is the selected authority for a defined responsibility;
- `COMPOSE`: it participates in one governed composed path;
- `FEDERATE`: it remains independently authoritative for an explicitly partitioned responsibility;
- `RETIRE`: it is excluded from the final execution topology with migration/cleanup evidence.

Every discovered candidate appears exactly once. A missing, duplicate, unknown, or contradictory disposition fails. `SELECT`, `COMPOSE`, and `FEDERATE` records bind exact interfaces, authorities, consistency, failure/recovery, and calling boundaries. `RETIRE` records prove no active dependency or authority remains.

The topology unifies logical product behavior, state/data authority, identity, permissions, consistency, failure/recovery, and calling boundaries. It does not require physical consolidation. A modular service set, monolith, federation, edge/client split, or mixed topology is valid when its logical contract and evidence are complete.

The words `CORE` and `EXTRA` remain Workflow business-necessity classifications. This design does not create a Product Backend/Core technical layer and does not rename a backend “CORE.”

## 13. Feature Slice remains the progress unit

Each Slice has exactly one class: `PRODUCT` or `OPERATIONS`. A cross-domain change uses linked Slices rather than a third or mixed class. Both inherit exact Product Baseline, topology, configuration, Adapter, candidate, UI/Workflow/Simulation, Impact, D0–D3, and Owner-acceptance evidence where applicable.

### 13.1 `PRODUCT` Slice

```text
actor through real UI, or applicable Product Agent
→ governed integration boundary
→ API/MCP-backed Workflow capability
→ real state/data/side effect
→ visible actor result
→ Simulation exception/recovery coverage
→ evidence and acceptance
```

A Product Agent route must prove the same real underlying product capability and may not replace Workflow with model output. Static prompts, mock tool calls, simulated state, or a conversational transcript alone are demonstrations.

### 13.2 `OPERATIONS` Slice

```text
real telemetry/log/event
→ Operations Agent observation and diagnosis
→ typed proposal
→ exact Policy and authorization decision
→ deterministic cataloged maintenance action
→ postcondition verification
→ rollback/fallback when required
→ append-only audit evidence and visible status
```

Every 2.8 project has at least one accepted required Operations Slice proving the real connected path. Read-only status explanation may be one Slice; it is insufficient by itself because the minimum capability includes an authorized deterministic action, verification, rollback route, and audit.

## 14. Simulation, UI, mutability, and impact

Simulation covers the same product/operations capability, state, authorization, failure, fallback, recovery, event, and audit semantics. It remains `VERSIONED_MUTABLE`; it is not the production backend, Agent memory, Runtime attestation, or an Agent-authored self-verification system.

The existing mutability rules remain:

```text
UI = LOCKED
Workflow = CONTROLLED_MUTABLE
Simulation = VERSIONED_MUTABLE
Calabash = LIVING_WITH_IMPACT_TRACE
```

Runtime, Adapter, model, Policy, Action Catalog, private-memory boundary, permission, credential, topology, and Agent applicability changes enter the existing Impact Analysis. Only affected layers and evidence are invalidated and reverified. No Agent may autonomously change a locked UI or restore Owner material.

## 15. Failure, degradation, fallback, and recovery

Every applicable Agent has explicit states and evidence for healthy, degraded, unavailable, killed, recovering, and replaced behavior. The system must distinguish model unavailability, Adapter failure, tool failure, authorization denial, telemetry loss, memory isolation failure, action failure, rollback failure, and audit failure.

Default continuity rules are:

- Operations Agent failure is visible, alertable, and recoverable. It does not by default stop core user business behavior.
- Product Agent failure stops core business behavior only when Calabash explicitly classifies that Product Agent capability as CORE and defines no accepted non-Agent fallback.
- EXTRA or optional Product Agent behavior degrades without falsely reporting CORE failure.
- No fallback expands permissions, merges Agents, bypasses Scorpion, uses stale credentials, disables audit, or silently converts a proposal into an action.
- Kill Switch activation is Owner/runtime-control authority outside Agent self-control. Recovery requires exact root authority and new current evidence.

## 16. Security and Delivery

The existing centralized security and Delivery gates remain authoritative. Agent-native coverage adds exact candidate/configuration/topology/Adapter/surface binding for:

- prompt injection and instruction-boundary bypass;
- privilege escalation and authorization confusion;
- Product/Operations cross-Agent memory leakage;
- raw-session, prompt-cache, retriever, vector-index, and credential leakage;
- tool and secret protection;
- model drift, substitution, and unavailability;
- Runtime/Adapter drift and replacement;
- deterministic-action integrity and confused-deputy risks;
- Policy and Action Catalog bypass;
- isolation, event redaction, provenance, and audit integrity;
- fallback, rollback, recovery, and Kill Switch behavior.

A later material change to Agent applicability, Policy, Action Catalog, memory/credential boundary, Adapter, Runtime, model capability, topology, event schema, or Agent attack surface invalidates affected closure, Post-Security Owner Acceptance, and `DELIVERY_READY` under the existing security invalidation rule.

Delivery packages include only approved product/runtime artifacts and runtime-neutral configuration needed by the customer. Secrets, private memory, raw prompts, construction-Agent evidence, internal LCCoding/Calabash/Loop assets, and unapproved Runtime internals remain excluded. Delivery Q&A records customer Runtime responsibility, model/provider availability, credential ownership, fallback, Kill Switch operation, audit retention, and replacement route without inventing legal terms from silence.

## 17. Compatibility and copy-on-write migration

### 17.1 Closed phase-ID policy

| Project schema | Read phase ID | Write phase ID | Compatibility status |
|---|---|---|---|
| `2.6.0` | `ENGINEERING_RUNS` | none by 2.8 tooling | `SUPPORTED_LEGACY` |
| `2.7.0` | `ENGINEERING_RUNS` | none by 2.8 tooling | `SUPPORTED_LEGACY` |
| `2.8.0` | `REAL_PRODUCT_INTEGRATION` | `REAL_PRODUCT_INTEGRATION` | `CURRENT` after version cut |

Schema determines the exact phase tuple. Readers never infer schema from a phase ID and never accept both IDs in one schema. A 2.8 writer never emits `ENGINEERING_RUNS`.

The existing `lc-coding/bi/release/loop-contract-identities.json` remains the only compatibility asset. It evolves in place to carry exact 2.6/2.7/2.8 status adapters and unchanged execution-method identities. Python, Rust, TypeScript tests, and PowerShell verification consume or mechanically validate that one asset; no second phase adapter table or compatibility JSON is introduced.

### 17.2 Migration

2.7→2.8 migration is copy-on-write:

1. freeze the exact 2.7 source and evidence pointers;
2. create an external candidate target that does not overlap source or generated output;
3. preserve existing bytes as historical evidence;
4. write only 2.8 schema and `REAL_PRODUCT_INTEGRATION` into the candidate;
5. create exact Agent applicability/configuration/topology/Adapter obligations;
6. reuse only evidence whose identity, authority, environment, scope, and meaning remain valid;
7. leave Operations Agent integration, Agent isolation, new security surfaces, and other unproved conditions incomplete;
8. validate the entire candidate before publishing the target.

A 2.7 project remains readable but cannot claim 2.8 until the required Operations Agent path, accepted configuration, final production topology, Runtime Adapter attestation, isolation, affected verification, security closure, and migration evidence are current. Old receipts are not rewritten or promoted.

Rollback discards or isolates an unaccepted 2.8 candidate and continues from the original 2.7 authoritative state and pointers. No 2.8 state flows back into 2.7.

## 18. Built-in BI minimal projection

The BI remains a read-only sanitized projection and keeps its compact window, interaction model, language behavior, protected reports, and authority boundary. It adds no Agent control.

For 2.8 it minimally projects these facts inside the existing Canonical Candidate protected report:

- Operations Agent integration status;
- Product Agent applicability and, when applicable, integration status;
- Runtime Adapter safe identity/version record;
- dual-Agent isolation status;
- separate `PRODUCT` and `OPERATIONS` Slice completion metrics.

The DTO exposes only safe IDs/version and normalized states/counts. It excludes prompts, memory, sessions, model inputs/outputs, credentials, paths, hashes, evidence bodies, events, tool arguments, Runtime diagnostics, and controls. Existing 2.6/2.7 Snapshots remain strict readable inputs; 2.8 uses the new phase ID. CSS tokens, 300×480 logical content baseline, Pin/Refresh/Open/Back, focus, scroll, and visual composition remain unchanged except for the additional report rows.

## 19. Rejected alternatives

### 19.1 Mandatory monolithic Product Backend

Rejected because final integration needs one logical authority contract, not one physical process. It would conflict with legitimate composed/federated products and with Workflow `CORE`/`EXTRA` terminology.

### 19.2 One Agent with dual memory or role switching

Rejected because a shared root identity, session, credential, prompt cache, retriever, or writable memory permits confused authority and leakage. Logical Agent independence is mandatory even when model/Runtime code is shared.

### 19.3 LCagent lock-in

Rejected because LCCoding is a cross-platform method standard. LCagent may be a reference Runtime, but another Runtime is accepted by the same Adapter and evidence contract.

### 19.4 Default autonomous operations

Rejected because diagnosis is not authorization. Operations actions default to exact Owner approval; only individually bounded low-risk actions may receive Calabash pre-authorization.

### 19.5 Agent dashboard as Operations integration

Rejected because a dashboard proves observation only. The minimum Operations path includes a real deterministic action, verification, rollback route, and audit.

### 19.6 Agent-owned root configuration

Rejected because it makes the controlled system the authority over its own identity, permissions, Scorpion constraints, credentials, and Kill Switch.

## 20. Acceptance criteria

The 2.8 method implementation is acceptable only when all statements below are mechanically true:

1. Exactly four lifecycle phases remain; no new gate or status authority exists.
2. Exact 2.8 new writes use `REAL_PRODUCT_INTEGRATION`; exact 2.6/2.7 reads use `ENGINEERING_RUNS`; cross-schema/hybrid inputs fail.
3. SLK/CLK/GLK remain cross-phase execution methods and are not Agent/lifecycle nodes.
4. Construction, Product, and Operations Agents are disjoint roles with closed applicability rules.
5. Every 2.8 project has a real accepted Operations Agent path.
6. A Product Agent is required only when Calabash says it applies; CORE Product Agent capability is real before Product Baseline.
7. Product and Operations Agents have distinct required isolation identities and only typed/minimal/audited cross-Agent events.
8. Root configuration and protected controls cannot be changed by an Agent.
9. The Agent Configuration Baseline, Action Catalog, final topology, Runtime Adapter attestation, Feature Slice, status, Verification, and security evidence join the same exact candidate.
10. Every relevant backend has exactly one `SELECT`, `COMPOSE`, `FEDERATE`, or `RETIRE` disposition.
11. `PRODUCT` and `OPERATIONS` Slices prove their respective real routes; mocks and self-reports fail.
12. Operations actions require exact Owner approval or narrowly evidenced Calabash pre-authorization and always include verification, rollback route, and audit.
13. Prompt/tool/memory/privilege/model/Runtime/isolation/fallback/Kill Switch surfaces are covered by current security evidence.
14. Agent/Runtime changes invalidate only affected evidence but cannot be silently preserved.
15. The BI reads 2.6/2.7/2.8 strictly, writes nothing, shows only the five approved Agent-native summaries, and retains the existing visual/interaction boundary.
16. Migration preserves the 2.7 source and old evidence bytes, creates no synthetic completion, and can roll back by discarding the candidate.
17. Fake/reference Adapter tests require no external secret; real Runtime deployment remains a separate Owner-authorized action.
18. Full Python, Rust normal/release, TypeScript, DOM, visual, package, installer-smoke, repository, integrity, migration, release, and zero-write preflight gates pass before formal release.
