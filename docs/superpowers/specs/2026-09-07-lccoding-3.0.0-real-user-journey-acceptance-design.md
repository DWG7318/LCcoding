# LCCoding 3.0.0 Real User Journey Acceptance Design

**Status:** Owner decisions are approved; this written design awaits Owner review before implementation planning.

**Base:** LCCoding `2.8.0`, commit `b8ecc366347682deea93eb64b3f0dd9d466e3aaa`.

**Target:** LCCoding `3.0.0` method and built-in BI candidate.

**Document role:** historical design provenance only. It does not change the current method, migrate a project, install the built-in BI, release LCCoding 3.0.0, or create acceptance evidence. `SPEC.md` remains the sole semantic authority after, and only after, an accepted implementation transfers these decisions into active clauses and mechanical contracts.

## 1. Problem statement

LCCoding 2.8 has four lifecycle phases. Real Product Integration joins Workflow, UI, Simulation, backend authority, state, data, permissions, and applicable Product/Operations Agents into a real product. Its D0-D3 evidence and per-Run Owner receipts prove engineering claims, while Delivery Preparation later performs centralized security closure, delivery decisions, and package protection.

What 2.8 does not define is one bounded, product-wide, black-box acceptance phase that behaves like a real user instead of reading code or trusting engineering evidence. The current phrase `Independent layered Verification → Owner Acceptance` can be interpreted as sufficient even when nobody has opened the actual product, started at the home page, exercised the complete user journeys, and judged every visible response from screenshots.

This gap permits four recurrent failures:

1. Code, DOM, API, or test assertions pass while the real product cannot be used from beginning to end.
2. UI, Workflow, and Backend are locally correct but disagree in the user-visible journey.
3. A late product defect has no stable number, screenshot, correction history, or full-round retest evidence.
4. Delivery Preparation begins before the product has passed a real-user experience verdict.

LCCoding 3.0 closes the gap with a fifth lifecycle phase and a bounded real-user journey acceptance protocol. It reuses prior engineering evidence and does not rerun lower-level verification.

## 2. Decision summary

The 3.0 lifecycle is exactly:

```text
INITIAL
→ PRODUCT_FORMATION
→ REAL_PRODUCT_INTEGRATION
→ REAL_USER_JOURNEY_ACCEPTANCE
→ DELIVERY_PREPARATION
→ Delivery
```

The new fourth phase starts only after the required Real Product Integration Run aggregate is current for one exact candidate. It operates the real product through its visible UI as a real user would, records the visible result after each meaningful action, assigns every defect a stable `40001+` identity, repairs defects in user-experience order, and restarts the next acceptance round from the home page.

The existing Delivery Preparation phase moves from fourth to fifth without changing its centralized security, Post-Security Owner Acceptance, delivery Q&A, package protection, or `DELIVERY_READY` meaning.

The built-in LCCoding BI is upgraded in the same 3.0 work so the existing four-phase projection cannot misrepresent a five-phase project. The BI remains a read-only projection, keeps its existing visual language, and gains exact schema-selected 2.8/four-phase and 3.0/five-phase behavior. This is a compatibility adaptation, not a visual redesign or control-plane expansion.

## 3. Goals

1. Make real-user product behavior a first-class lifecycle condition before Delivery Preparation.
2. Validate visible behavior from the real product surface rather than infer it from code, DOM, fixtures, APIs, logs, or tests.
3. Cover all required, applicable user journeys through a bounded journey graph derived from Calabash, Simulation, Product Baseline, Feature Slices, and accepted integration evidence.
4. Preserve every observed defect, screenshot, correction, exemption, and retest result under one stable identity.
5. Repair user-visible defects in the order `UI → Workflow → Backend/Core` while allowing one cross-layer correction when the root cause spans layers.
6. Restart every post-repair acceptance round from the home page so earlier behavior is re-proved on the new exact candidate.
7. Keep Owner participation small: the Agent performs the journeys and analysis; the Owner receives one conclusion and makes the phase decision.
8. Permit a small, explicit human assist for Codex viewport preparation without turning the Owner into the tester.
9. Preserve existing D0-D3, per-Run acceptance, centralized security, Post-Security acceptance, and Delivery protections without duplicate verification.
10. Migrate 2.8 projects explicitly and copy-on-write; never relabel old evidence as 3.0 acceptance.
11. Keep the built-in BI usable by projecting the new phase, its evidence summary, and the shifted Delivery Preparation phase without changing its read-only authority.

## 4. Non-goals

- No visual redesign, new BI navigation model, control plane, evidence editor, screenshot browser, or project-write capability.
- No replacement of D0, D1, D2, D3, Loop Owner Acceptance, centralized vulnerability closure, or Post-Security Owner Acceptance.
- No second implementation of Playwright, unit, integration, API, contract, static, security, or source-code tests.
- No claim that a screenshot proves invisible state, authorization, persistence, or backend correctness; those remain prior engineering responsibilities.
- No unbounded exploratory clicking, random fuzzing, arbitrary page crawling, or attempt to enumerate physically impossible input combinations.
- No new construction role, browser Runtime, crawler service, recording daemon, status authority, or execution method.
- No mandatory browser vendor, screen resolution, operating system, or model provider.
- No Owner requirement to repeat the product test manually.
- No release or global deployment of LCCoding 3.0 as part of the design or planning Cell.

## 5. Five-phase semantics

### 5.1 Phases 1-3

`INITIAL`, `PRODUCT_FORMATION`, and `REAL_PRODUCT_INTEGRATION` retain their 2.8 meanings. Real Product Integration still begins with Feature Slice, selects the production execution topology, joins real UI/Workflow/Simulation/state/data/Agents, completes required Runs, and produces the exact accepted integration candidate.

D3 may prove the seams and actor journey required by one Run or Slice. It is not the product-wide fourth-phase acceptance round and cannot substitute for it.

### 5.2 Phase 4 — `REAL_USER_JOURNEY_ACCEPTANCE`

Phase 4 treats the accepted integration candidate as a running product. Its question is not “does the implementation satisfy its engineering contract?” but “can the intended user actually complete every required journey and receive the expected visible result?”

The phase owns:

- journey coverage selection;
- real visible operation;
- per-action screenshot evidence;
- visible-result judgment;
- `40001+` defect identity and history;
- correction routing and priority;
- full-round restart after correction;
- the final real-user journey verdict presented to the Owner.

It does not own source-level verification, security closure, delivery decisions, or packaging.

### 5.3 Phase 5 — `DELIVERY_PREPARATION`

Delivery Preparation starts only after current Phase-4 Owner acceptance for the exact candidate. It retains the 2.8 sequence:

```text
Centralized vulnerability audit
→ remediation
→ independent re-audit and vulnerability closure
→ Post-Security Owner Acceptance
→ Delivery Method Q&A
→ runtime/license/package protection
→ DELIVERY_READY
```

If Phase-5 remediation changes visible behavior, Impact Analysis invalidates the affected Phase-4 journeys. The project reruns the affected journey from its home-page entry and performs the existing critical smoke. A broad or unknown impact returns the product to a complete Phase-4 round. Unaffected journey evidence is not mechanically rerun merely because security work occurred.

## 6. Phase-4 entry contract

Phase 4 may begin when all of the following refer to one exact candidate:

1. Product Baseline and Integration Baseline are current.
2. Every required Real Product Integration Run has current D0-D3 and Loop Owner Acceptance evidence.
3. `ALL_REQUIRED_RUNS_ACCEPTED` is current for that candidate.
4. The real product can be started in an acceptance environment with the required services, accounts, permissions, data, and external dependencies.
5. Calabash, Simulation scenarios, Workflow/UI maps, Feature Slices, and accepted integration evidence are sufficient to derive the required journey graph.
6. The acceptance operator has a real browser surface capable of screenshots and visible-result inspection.

A missing acceptance-environment fact is resolved as ordinary Phase-4 preparation work. It is not silently replaced by code inspection or a mocked page.

## 7. Bounded journey graph

The acceptance operator creates one candidate-bound journey coverage table inside the Phase-4 acceptance record. It is a directed graph, not an unbounded crawler plan. Each journey records:

- stable Journey ID;
- starting actor and permission role;
- home-page or product-entry starting point;
- preconditions and test data;
- ordered visible actions;
- expected visible state after each meaningful action;
- expected final business outcome;
- applicable exception, recovery, empty, invalid-input, and permission-denied routes;
- trace to Calabash capability, Simulation scenario, Workflow/UI map, Feature Slice, and accepted Run evidence;
- applicability disposition when a route is intentionally out of scope.

Coverage includes every required CORE user journey, every delivered EXTRA journey represented as product capability, authentication/onboarding when applicable, primary business operations, navigation, state continuation, error/recovery behavior, permissions, and critical Operations/Product Agent surfaces visible to the applicable actor.

The graph bounds the work. The operator follows required and applicable routes and records discoveries, but does not improvise unlimited permutations. Newly discovered meaningful routes are added to the same coverage table with a trace and are included in the next complete round.

## 8. Real-browser operation and visual evidence

Acceptance uses the real product UI. The verdict for a visible step comes from the rendered result that a user can see. Source code, DOM queries, API responses, database queries, console logs, and prior automated tests may help diagnose a recorded defect, but they do not replace the visible Phase-4 proof.

For each meaningful state-changing action—navigation, completed input, click, submit, selection, upload, confirmation, or equivalent—the operator:

1. performs the action through the visible interface;
2. waits for the user-visible result to settle under the product's normal behavior;
3. captures a screenshot immediately after that result;
4. records candidate, round, Journey ID, Step ID, action, expected result, observed result, URL or visible location, actor, viewport, and screenshot digest;
5. marks the step `PASS`, `DEFECT`, `BLOCKED_BY_DEFECT`, or `NOT_APPLICABLE` with evidence.

Typing is treated as one completed input action rather than one action per keystroke. Secrets and personal data are not used as screenshot evidence; acceptance uses test identities and safe test data.

### 8.1 Codex viewport preparation

When Codex's in-app browser is used, the preferred desktop acceptance setup is:

```text
Expand the right browser panel to full width
→ press F11 for application full screen
→ record the resulting viewport dimensions
```

The Agent first attempts any available supported shortcut or control. When Codex automation cannot operate the outer application chrome, the Agent may ask the Owner to perform only these viewport controls. This is environment preparation, not product operation, acceptance judgment, or Owner retesting. The Agent performs the journeys after the viewport is ready.

The verified reference on the current machine expanded the in-app viewport from `630×918` to `1417×918`, then to `1936×934` after `F11`. These measurements demonstrate feasibility; they are not a mandatory resolution for other machines or projects.

## 9. Acceptance rounds

Round 1 always starts from the defined home-page/product entry and a declared initial test state. The operator follows every required reachable journey. A defect blocks only the dependent route unless it prevents login, navigation, environment availability, or all remaining work; independent reachable routes continue so one round can collect more than one factual defect.

After the round:

1. consolidate every observed defect and its evidence;
2. order correction work by the earliest affected user layer: UI first, Workflow second, Backend/Core third;
3. diagnose the actual cause using engineering evidence;
4. route each correction through the normal LCCoding phase authority and an explicitly selected execution method when a Run is needed;
5. allow one correction to change multiple layers when that is necessary to restore one coherent user journey;
6. create a new exact candidate and close the applicable engineering re-verification;
7. start the next acceptance round again from the home page and execute the complete required journey graph.

No Phase-4 repair round resumes halfway through the prior route. Prior screenshots remain historical defect evidence and are not reused as current-round PASS evidence.

## 10. Defect numbering and durable records

The first Phase-4 defect is `40001`; subsequent defects increase monotonically within the project. An ID is never recycled when a defect is rejected, merged, deferred, reopened, or found to share a root cause.

The 3.0 method introduces two project artifacts and one evidence directory:

| Artifact | Responsibility |
|---|---|
| `.lccoding/REAL-USER-JOURNEY-ACCEPTANCE.md` | current candidate, journey coverage, round table, final verdict, Owner decision, and pointers to defects/evidence |
| `.lccoding/REAL-USER-JOURNEY-DEFECT-LOG.md` | append-only `40001+` defect history, cause, affected layer, correction, exemption, candidate lineage, and retest result |
| `.lccoding/evidence/real-user-journey/<round>/<journey>/` | screenshots and bounded action evidence for the exact round |

Each defect entry records at least:

- defect ID, discovery time, candidate, round, Journey ID, and Step ID;
- expected and observed visible behavior;
- screenshot path and SHA-256;
- severity, reachability impact, and blocking scope;
- initial user-layer classification and diagnosed root cause;
- affected UI, Workflow, Backend/Core, data, permission, or Agent surfaces;
- correction Run or change identity;
- D0-D3 or other affected engineering re-verification references;
- correction candidate and retest round;
- result `OPEN`, `FIXED_VERIFIED`, `OWNER_EXEMPTED`, `DEFERRED`, `MERGED_INTO`, or `REOPENED`;
- exemption authority, reason, user impact, and recovery condition when applicable.

All participants record their own factual work into the existing project record flow. `status.json` remains the single project-status authority and stores only Phase-4 state plus current artifact pointers, not screenshots or duplicate defect bodies.

## 11. Defect priority and cross-layer repair

`UI → Workflow → Backend/Core` is the correction queue priority because final acceptance is user-experience-led. It does not require a cosmetic UI patch when the actual defect originates in Workflow or Backend.

For one defect:

- classify the earliest visible failure layer;
- diagnose the complete cross-layer cause;
- repair every necessary affected layer as one coherent correction;
- revalidate the affected engineering contracts;
- rerun the complete Phase-4 journey round from the home page.

An earlier-priority defect is normally addressed before a later-priority defect. The Supervisor may reorder corrections when dependency facts show that a later-layer root fix is required to make the earlier UI correction real; the record explains the dependency rather than presenting the order change as a silent exception.

## 12. Verdict and Owner boundary

The Agent reports one concise Owner-facing conclusion containing:

- exact candidate;
- number of complete rounds;
- required journeys passed/failed/not applicable;
- defects discovered, fixed, open, deferred, and exempted;
- material user impact of any exemption;
- evidence-record path;
- recommendation `ACCEPT`, `REWORK`, or `DEFER`.

The Owner is not asked to repeat the product test. The Owner chooses one terminal Phase-4 result:

- `REAL_USER_JOURNEY_ACCEPTED`;
- `REAL_USER_JOURNEY_REWORK`;
- `REAL_USER_JOURNEY_DEFERRED`.

`REAL_USER_JOURNEY_ACCEPTED` is the only normal entry to Delivery Preparation. It binds the exact candidate, journey graph, final complete round, evidence digests, defect ledger, and any explicit Owner exemptions. A later affected product change invalidates this result according to impact.

## 13. Verification de-duplication and independence

Phase 4 consumes current D0-D3 and Run receipts as entry evidence. It does not rerun their unit, source, contract, compilation, API, integration, or invisible-system checks.

The acceptance operator must not use implementation reasoning as the verdict. A Worker or Checker from earlier Runs may provide technical diagnosis after a defect is recorded, but the visible retest is performed in a fresh acceptance context against the new exact candidate. Screenshot evidence, defect decisions, and final journey verdict remain candidate-bound.

The required independence is judgment isolation, not creation of a new permanent role. LCCoding may use an appropriate existing Agent/context to perform the acceptance so long as it has not authored the candidate and receives only the journey contract, runnable environment, and necessary product-use information before testing.

## 14. 2.8-to-3.0 migration

Migration is explicit and copy-on-write:

1. preserve the complete 2.8 project and evidence;
2. validate the 2.8 source under the 2.8 schema;
3. create a 3.0 candidate with five phase identities;
4. retain Phases 1-3 evidence only when candidate and impact identity remain valid;
5. initialize Phase 4 as unproved with no fabricated journey, screenshot, defect, or Owner result;
6. move existing Delivery Preparation state to Phase 5 only when its source evidence remains valid and the project has not yet crossed the new Phase-4 boundary;
7. require real Phase-4 execution before a migrated project may newly enter or re-enter Delivery Preparation under 3.0;
8. preserve 2.8 as strict read-only compatibility input; 3.0 writers emit only 3.0 shapes.

Existing 2.8 completion, D3, Run Owner acceptance, critical smoke, or Post-Security acceptance cannot be renamed into `REAL_USER_JOURNEY_ACCEPTED`.

## 15. Built-in BI 3.0 adaptation

The built-in React/Vite/Tauri BI is upgraded with the method so it remains a truthful read-only projection. The existing layout, visual hierarchy, styling, responsive behavior, pin behavior, desktop boundary, and non-authoritative posture remain recognizable. The implementation does not use the version change as permission for a redesign.

Schema selects the view:

- an exact 2.8 project continues to render the existing four phases and 2.8 meanings;
- an exact 3.0 project renders five phases in the approved order;
- mixed, inferred, or partially upgraded phase shapes fail closed instead of being silently normalized;
- the BI never writes status, acceptance, defect, screenshot, or Owner-decision evidence.

For a 3.0 project, the new fourth phase appears between Real Product Integration and Delivery Preparation. Its compact read-only detail contains:

1. journey coverage state;
2. acceptance-environment readiness;
3. current/last complete round and exact candidate;
4. required journey totals and pass/fail/not-applicable counts;
5. defect totals by open, fixed-verified, exempted, deferred, and reopened state;
6. final recommendation and Owner terminal result;
7. sanitized pointers to the acceptance record and defect log.

The BI does not render every screenshot or duplicate the full defect ledger. Evidence stays in project artifacts; the BI shows only enough sanitized information to understand phase state and find the authoritative record.

The fifth phase continues to show the existing security, Post-Security Owner Acceptance, Delivery Q&A, package protection, and `DELIVERY_READY` rows. Their semantics do not change merely because their phase ordinal moves from four to five.

The adaptation includes the TypeScript snapshot model/parser, catalog labels, React projection, Rust/Tauri record parser and projection, exact 2.8/3.0 compatibility assets, DOM tests, visual tests, Rust tests, packaging identity, and formal candidate build checks needed to keep the desktop BI runnable. Actual installation, tag creation, GitHub Release creation, and global deployment remain later release actions.

## 16. Implementation boundaries

The later implementation plan will separate at least these reviewed units:

1. semantic authority and five-phase contracts;
2. Phase-4 templates and evidence schema;
3. read-only validators and `40001+` identity rules;
4. status/phase projection and 2.8-to-3.0 migration;
5. BI schema compatibility and Rust/TypeScript projection;
6. minimal five-phase React UI adaptation with unchanged visual language;
7. BI packaging identity and candidate build verification;
8. repository integrity, compatibility, and documentation.

Each unit will use focused RED/GREEN tests, mechanical hash updates, and narrow commits. The implementation plan will include BI source, test, and candidate-package work, but not installation, tag creation, GitHub Release creation, global Skill deployment, or migration of a real external project.

## 17. Acceptance criteria for the core upgrade

The LCCoding 3.0 core candidate is ready for a separate release decision when:

1. the canonical lifecycle contains exactly five phases in the approved order;
2. Phase 4 has one closed entry, coverage, operation, evidence, defect, repair, round-restart, verdict, and invalidation contract;
3. D3 and Phase 4 are mechanically and semantically distinct;
4. the new status/template/validator family remains subordinate to `status.json` as the single authority;
5. 2.8-to-3.0 migration preserves source evidence and initializes Phase 4 as unproved;
6. Phase 5 retains existing security and Delivery meaning;
7. user-visible acceptance is based on real rendered feedback and candidate-bound screenshots;
8. Owner assistance is limited to viewport preparation when outer Codex chrome cannot be automated;
9. exact 2.8 projects remain readable as four phases and exact 3.0 projects render five phases without inference;
10. the BI displays the Phase-4 summary and shifted Phase-5 rows while preserving its read-only boundary and existing visual language;
11. TypeScript, DOM, visual, Rust, packaging-contract, repository, migration, and integrity tests pass;
12. a candidate BI package can be built and its version/provenance checked without installing or publishing it;
13. no implementation step claims release, deployment, installation, or migrated-project completion.
