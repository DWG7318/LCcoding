# LCCoding 4.0.1 Ponytail External Skill Governance Design

Date: 2026-09-13
Status: Owner-approved design candidate
Target: LCCoding 4.0.1

## 1. Problem

LCCoding already governs product lifecycle work and selects one compatible Loop execution method for each Run. It does not yet distinguish its native method family from third-party Agent Skills, so an AI may load or apply an outside Skill without first establishing whether the Owner wants that additional influence on construction.

Ponytail is useful for reducing unnecessary implementation, abstraction, dependency, and code, but it is not part of the LCCoding method family. Treating it as native would silently change how a project is built. Treating every available external Skill as an LCCoding option would create an unreviewed catalogue and repeat the method bloat this change is intended to avoid.

The current LCCoding method-selection wording also retains an obsolete CLK description based on Stages and full barriers. That wording no longer matches the current CLK method and should not remain copied into LCCoding.

## 2. Decision

LCCoding 4.0.1 adds one general authorization boundary for external Skills and admits exactly one named curated external Skill: Ponytail.

The native LCCoding family is:

- LCCoding;
- Calabash;
- SLK, CLK, and GLK;
- contracts, templates, scripts, references, and BI shipped as part of LCCoding.

Ponytail remains external. No other named external Skill is added by this release.

## 3. Owner inquiry

During Proposal Readiness, AI may identify Ponytail as relevant after examining the project, existing engineering conventions, expected complexity, and risk of unnecessary construction. The AI presents one concise inquiry before Ponytail is first loaded, installed, invoked, injected into another Agent, or used to govern project work.

The inquiry states:

- the exact Skill name and source;
- why Ponytail is or is not recommended for this project;
- the proposed project, Run, or narrower application scope;
- the expected reduction in unnecessary engineering;
- material trade-offs, including the risk of under-building or conflicting with existing project rules;
- the proposed Ponytail mode when the available Skill exposes modes.

Presenting this explanation and asking the question is not use of Ponytail. Public, read-only examination sufficient to make an informed recommendation is also not activation.

The Owner may approve, reject, or narrow the proposal. Rejection or non-adoption leaves the project on ordinary LCCoding-native construction and does not stop lifecycle progress.

## 4. Authorization lifetime

One affirmative Owner answer authorizes the identified Ponytail identity and declared scope for the current project. Repeated use inside that recorded scope does not trigger repeated questions.

A materially different Ponytail identity, a broader scope, or a changed mode that materially alters behavior requires a new inquiry. Authorization to use Ponytail does not expand product scope, repository permissions, system permissions, release authority, or any other Owner boundary.

The result is recorded in the existing `PROPOSAL-READINESS.md`. The record identifies the decision, source or identity available at decision time, approved scope, mode if applicable, recommendation rationale, and material trade-offs. This design creates no new artifact, phase, gate, status system, or role.

For an existing project entering LCCoding after its original proposal work, the same single inquiry is made at the first point Ponytail is proposed for that project, and the result is added to the existing readiness record or its governed continuation record.

## 5. Ponytail boundary

Ponytail influences implementation economy. It may encourage reuse of existing code, standard-library or platform-native capability, already-adopted dependencies, and the simplest implementation that reliably satisfies the accepted objective.

Ponytail does not decide product meaning, delete accepted requirements, redefine Calabash, choose the Loop topology, change SLK/CLK/GLK roles, replace D0-D3 or Owner acceptance, weaken security or delivery constraints, bypass UI authority, or supply permission for external actions.

Ponytail is not a mature-external-tool discovery and adoption system. Choosing a new external dependency, service, or commercial product continues to require the normal technical, security, licensing, data, operational, and Owner-authority analysis applicable to that choice.

Ponytail also remains distinct from SLK's reasonable minimum construction guidance. SLK controls the necessary construction route, scope, and engineering activity when entering completed or partly completed work; Ponytail affects implementation choices inside work where its use has been approved.

## 6. Curated admission rule

The 4.0.1 documentation may name Ponytail and no other external Skill as an admitted option. Generic policy may state that any future external Skill requires Owner authorization before use, but it does not make unnamed Skills recommended, approved, registered, or part of LCCoding.

Adding another named external Skill requires a later, explicit review of its purpose, overlap, conflicts, authority effects, maintenance source, and value to LCCoding. It is not added incidentally while editing another feature.

An external Skill already installed globally is still external to an LCCoding project. Availability is not project authorization.

## 7. Execution-method wording correction

LCCoding retains only stable topology-level descriptions and defers internal mechanics to the selected method's current, locked identity:

- SLK represents one serial Loop path;
- CLK represents multiple independently progressing Chains whose accepted results are fused as required by its current method contract;
- GLK represents a real dependency DAG whose eligible GO work starts from satisfied dependencies and converges through its final Fusion GO.

LCCoding no longer describes current CLK through Stages or full barriers. Before a Run locks a method identity, selection reads the latest applicable registered method information; after selection, the project locks the exact chosen identity and does not silently drift with later method releases.

## 8. Minimal implementation scope

Implementation should update only the existing authorities and consumers needed to make this behavior real:

- the canonical specification and compact main Skill entry;
- Proposal Readiness guidance and its existing template;
- execution-method selection guidance;
- focused tests and mechanical version, manifest, hash, changelog, and validation carriers required by the repository.

The built-in BI product behavior, lifecycle phase count, Calabash content, Loop-method repositories, and global Skill installation are outside this patch.

## 9. Acceptance

The 4.0.1 candidate is acceptable when mechanical checks establish that:

- Ponytail is the only named external Skill admitted by this change;
- first use requires an Owner inquiry and an affirmative recorded decision;
- asking about Ponytail is distinguishable from invoking it;
- rejection or non-adoption continues through native LCCoding without a new stop condition;
- one authorization is reusable only inside its recorded project scope;
- no new phase, gate, role, status system, or artifact has been introduced;
- Ponytail does not replace product authority, Loop topology, verification, acceptance, security, or delivery rules;
- current CLK is not described through Stages or full barriers;
- repository integrity, version consistency, migration compatibility, and the existing regression suite remain valid.

Tests should verify the behavioral boundary and authority relationship rather than freeze incidental prose beyond what is required for identity and compatibility.

## 10. Non-goals

This patch does not install or bundle Ponytail, enable it by default, copy its prompt into LCCoding, create a general external-Skill marketplace, admit additional named external Skills, rank arbitrary Skills, redesign construction methods, or change the LCCoding lifecycle.
