# LCCoding 3.1.0 Applicability and Service Topology Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade LCCoding from 3.0.0 to a 3.1.0 candidate that assesses method fit before project initialization and carries platform-completion, Personal-Agent, and applicable Service-Center routes through Calabash, Product Formation, Real Product Integration, Real User Journey Acceptance, and the read-only BI.

**Architecture:** Preserve one five-phase lifecycle and one shared Workflow/Backend/Core. Initial adds two named decisions without a new phase: applicability and product service strategy. Calabash owns one structured Service Route Map; 3.1 integration and journey evidence are route-faithful while exact 3.0 browser evidence remains supported as legacy. The BI adds only schema-selected step projection and sanitized route summaries, not a redesign or control plane.

**Tech Stack:** Markdown authority/templates, JSON contracts, Python 3 validators and migration, React 19, TypeScript 7, Vite 8, Vitest, Playwright, Rust 2024, Tauri 2, PowerShell 5.1/7, NSIS, Git.

---

## Fixed decisions

- Target version is `3.1.0`; `3.0.0` remains a supported legacy schema.
- The phase order remains `INITIAL`, `PRODUCT_FORMATION`, `REAL_PRODUCT_INTEGRATION`, `REAL_USER_JOURNEY_ACCEPTANCE`, `DELIVERY_PREPARATION`.
- Initial shows two primary strategies: `PLATFORM_COMPLETION` and `AGENT_COLLABORATIVE`; `MIXED` means both are required in one product, not a third architecture.
- Applicability results are `WHOLE_PRODUCT_FIT`, `BOUNDED_PRODUCT_FIT`, or `OTHER_METHOD_RECOMMENDED`. The last result rejects only use of the full method, not the engineering project.
- The Service Route Map route kinds are `DIRECT_PRODUCT`, `PERSONAL_AGENT`, and `SERVICE_CENTER`.
- One product strategy does not grant every action to every route. Required routes are selected per delivered journey under Calabash authority.
- Direct, Personal-Agent, and Service-Center routes converge on the same Workflow and Backend/Core capability; adapters and presentation may differ.
- Personal Agent, Product Agent, Operations Agent, and Service Center actor are distinct identities.
- Phase 4 remains named `REAL_USER_JOURNEY_ACCEPTANCE`; 3.1 changes it from browser-exclusive to route-faithful evidence.
- Screenshots remain required for meaningful visible actions. Structured messages, tasks, artifacts, authorization decisions, and audit events are first-hand evidence for non-visual Agent steps. Every accepted route still ends in a human-observable outcome.
- The normal correction order is `USER_SERVICE_BOUNDARY → WORKFLOW_ORCHESTRATION → BACKEND_CORE`; `USER_SERVICE_BOUNDARY` resolves to UI, Agent service behavior, or assisted-service behavior for the route.
- No new phase, construction role, execution method, Runtime, protocol mandate, second Workflow/Core, or BI visual redesign is introduced.
- This plan prepares a local 3.1 candidate. GitHub push, tag, Release, global Skill deployment, and persistent BI installation require separate release authority.

## Pre-change RED evidence

Three independent read-only pressure scenarios used only the accepted 3.0 `SKILL.md` and `SPEC.md`:

1. A headless compiler-only algorithm library was not rejected at method entry. The evaluator could enter Initial and only later discovered that mandatory UI, Product Baseline, Feature Slice, and browser journey rules made the full lifecycle impossible. This confirms the missing applicability boundary.
2. A Personal-Agent-first SaaS could form Workflow/API/MCP capability in Phase 2, but the evaluator found no honest way to accept its primary route in Phase 3 or 4 without inventing a browser action or treating API/log evidence as a forbidden substitute. This confirms the UI-centric integration and acceptance conflict.
3. A product promising direct Web, Personal Agent, and paid Service Center entry could be informally mapped onto the 3.0 skeleton, but the evaluator had to invent external Personal Agent, principal/delegate, Service Center tenant/operator, delegation, payment, and route-evidence semantics. This confirms that the current result is not unique or mechanically checkable.

These are the RED baselines for the skill change. The implementation is GREEN only when the same scenarios resolve through explicit applicability, identity, route, and evidence rules without adding a second product architecture.

## Target 3.1 status and route shape

The 3.1 authoritative status adds only three scalar summaries:

```json
{
  "lccoding_applicability": "PENDING",
  "product_service_strategy": "PENDING",
  "service_route_map": "PENDING"
}
```

Allowed current values are:

```python
APPLICABILITY = {"PENDING", "WHOLE_PRODUCT_FIT", "BOUNDED_PRODUCT_FIT"}
STRATEGY = {"PENDING", "PLATFORM_COMPLETION", "AGENT_COLLABORATIVE", "MIXED"}
ROUTE_MAP_STATE = {"PENDING", "DRAFT", "ADOPTED"}
```

`OTHER_METHOD_RECOMMENDED` is a pre-initialization assessment result and does not create a 3.1 LCCoding project status.

The 3.1 BI Initial layout is:

```json
[
  "LCCODING_APPLICABILITY_ASSESSMENT",
  "PROPOSAL_READINESS",
  "PRODUCT_SERVICE_STRATEGY",
  "PROJECT_INITIALIZATION",
  "INITIAL_READY"
]
```

Product Formation inserts `SERVICE_ROUTE_MAP_READY` after `CALABASH_DRAFT`. All five phase IDs remain unchanged.
